# Модуль «Учёт ассетов» (реестр объектов дворовой территории)

> _Составлено: 2026-08-02_

> Статус: **ТЗ, не реализовано.** Документ описывает то, что предстоит сделать,
> а не то, что уже работает.
>
> Источник данных для миграции: бот `asset-inventory-bot` (отдельный репозиторий,
> работает на profk с июля 2026). 159 объектов с координатами уже собраны.
>
> Площадка: **profk** (БД `profk_management`). Инсталляция на .105
> (`uk_management`) получит те же таблицы вместе с кодом, но без данных.

## 1. Назначение

Реестр физических объектов дворовой территории — фонарей, скамеек, урн, беседок —
с координатами и постоянными номерами, которые **наносятся краской на сами
объекты**.

Смысл не в самой инвентаризации. Смысл в том, что у объекта появляется имя,
одинаково понятное жителю, диспетчеру и электрику. Сегодня заявка звучит как
«сломался фонарь около беседки», и исполнитель ищет его на местности. С реестром
она звучит как «сломался фонарь `Y1L43`» — с точной координатой, категорией и
историей поломок.

Из этого следует важное свойство: **реестр поддерживается потоком заявок, а не
обходами**. Каждая заявка по объекту — отметка, что объект существует и в каком
он состоянии. Обходы нужны только для новых объектов и сплошной сверки, их
частота — 1–4 раза в год.

В УК сейчас **нет никакого учёта ассетов**. Ближайший по духу модуль — «Склад
материалов» (`docs/MATERIALS_MODULE.md`), его структура взята за образец.

### Границы (осознанные упрощения первой версии)

Не входит: QR-коды и таблички, интерфейс для жителей, планирование ремонта,
списание материалов на объект, оценка стоимости, паспорта оборудования,
фотофиксация «до/после». Всё это осмысленно, но каждое утраивает объём, а ценность
даёт уже связка «номер на объекте → заявка».

## 2. Что уже есть

**Данные.** 159 объектов, собранных за один обход 8 июля 2026 на территории ЖК
Yangi Olmazor (участок ~185×330 м): 114 фонарей, 33 скамейки, 9 урн, 3 беседки.
Из них **66 (41%) в состоянии «не работает» или «требует ремонта»** — это готовый
список работ, который сейчас лежит мёртвым грузом в CSV.

Ближайшие дома (`Yangi Olmazor 18V/19V/20V`, 17–62 м) уже заведены и в УК, и в
Infrasafe.

**Формат номера.** Введён 2 августа 2026, применён ко всем 159 объектам:

```
Y{код двора}{БУКВА категории}{номер}      например  Y1L43
```

Без дефисов и ведущих нулей — номер наносится по трафарету, каждый лишний символ
умножается на полторы сотни объектов. Буквы закреплены за категориями навсегда:

| Буква | Категория | Код |
|:-----:|-----------|-----|
| `L` | Фонарь | `LAMP` |
| `G` | Беседка | `GAZEBO` |
| `B` | Скамейка | `BENCH` |
| `U` | Урна | `URN` |
| `P` | Детская площадка | `PLAYGROUND` |
| `O` | Прочее | `OTHER` |

**Двор** — то, что бот называет «фазой». Это подтверждается географией: объекты
фазы 2 отстоят от фазы 1 примерно на 230 метров, то есть это отдельный участок
территории, а не логическая пометка.

**Статусы:** `Исправен`, `Требует ремонта`, `Не работает`.

## 3. Принятые решения

Согласовано с владельцем 2026-08-02. Решения, а не предположения — если что-то
из этого меняется, меняется и объём работ.

| Вопрос | Решение | Следствие |
|--------|---------|-----------|
| Формат номера | `Y1L43`, без ведущих нулей | ввод `Y1L043` должен нормализоваться в `Y1L43` |
| Кто указывает номер в заявке | **только сотрудники** | не нужны TWA-интерфейс, выбор по геолокации для жителей, QR |
| Где живёт код | внутри репозитория УК, таблицы в БД УК | `requests.asset_id` — обычный FK, без межсервисных вызовов |
| Справочник дворов | **свой, внутри модуля** | не зависим от таблицы `yards`; ссылка на неё опциональна |
| Полевой бот | **остаётся насовсем** | фаза C — переключить его с CSV на БД, а не писать сценарий в боте УК |
| Публичность карты | открыта без авторизации — принятый риск | отдельная веб-карта бота остаётся как есть |

## 4. Модель данных

Файл: `uk_management_bot/database/models/asset.py`.
Миграция: `alembic/versions/0009_assets.py` (следующий свободный номер).

### `asset_yards` — справочник участков

```
id            PK
code          SMALLINT  UNIQUE NOT NULL   -- попадает в номер: Y1, Y2
name          VARCHAR(200) NOT NULL
yard_id       FK yards.id NULL            -- опциональная связь с дворами УК
is_active     BOOLEAN NOT NULL DEFAULT true
created_at, updated_at
```

**`code` задаёт человек, это не автоинкремент.** Требование жёсткое: если двор
получит суррогатный `id` = 17, а на фонарях написано `Y1`, сойтись это уже не
сможет — номер на металле не переписать. Существующие данные требуют `code = 1`
и `code = 2`.

### `assets` — сам реестр

```
id              PK
asset_number    VARCHAR(16) UNIQUE NOT NULL  -- Y1L43, канонический вид
yard_code       SMALLINT NOT NULL            -- денормализация: номер самодостаточен
asset_yard_id   FK asset_yards.id NOT NULL
category        VARCHAR(20) NOT NULL         -- LAMP | GAZEBO | BENCH | URN | PLAYGROUND | OTHER
status          VARCHAR(30) NOT NULL         -- Исправен | Требует ремонта | Не работает
latitude        NUMERIC(9,6) NOT NULL
longitude       NUMERIC(9,6) NOT NULL
photo           JSON DEFAULT []              -- как media_files в requests
comment         TEXT NULL
legacy_id       VARCHAR(20) NULL             -- P1-LAMP-042, для сверки со старым CSV
installed_at    TIMESTAMPTZ NULL
created_by      FK users.id NULL
created_at, updated_at
```

`UNIQUE` на `asset_number` — глобальный, а не в пределах двора: код двора уже
внутри номера.

### `asset_number_counters` — выданные номера

```
yard_code   SMALLINT  \  PK (составной)
category    VARCHAR(20) /
last_number INTEGER NOT NULL
```

### `asset_status_history` — история состояний

```
id              PK
asset_id        FK assets.id NOT NULL
status_from     VARCHAR(30) NULL     -- NULL для первой записи
status_to       VARCHAR(30) NOT NULL
changed_by      FK users.id NULL
request_number  VARCHAR(15) FK requests.request_number NULL  -- если состояние изменила заявка
note            TEXT NULL
changed_at      TIMESTAMPTZ NOT NULL
```

История — не украшение. Без неё «этот фонарь ломался четыре раза за год» не
ответить, а это единственное основание менять, а не чинить в пятый раз.

## 5. Нумерация — критичные требования

Раздел вынесен отдельно, потому что это единственная необратимая часть модуля.
Номер попадает на металл; ошибка в нумерации исправляется не миграцией, а
повторным обходом с краской.

**Т-1. Номер никогда не выдаётся повторно.** Даже если объект удалён из реестра.
Счётчик `asset_number_counters.last_number` **только растёт**. Восстанавливать
счётчик как `MAX(номер)` по существующим строкам **запрещено**: удаление
последнего объекта освободит номер, и два разных фонаря в поле получат одну
цифру. Именно этот дефект был в боте до августа 2026 и чинился отдельно.

**Т-2. Выдача — в транзакции.** `SELECT … FOR UPDATE` по строке счётчика,
инкремент, вставка объекта. Два обходчика, одновременно добавляющие фонарь в
одном дворе, не должны получить один номер.

**Т-3. Ввод нормализуется, канон — короткий.** `y1l043`, `Y1L043`, `Y1L43` — это
один объект. Приводить к верхнему регистру и убирать ведущие нули номера.
Хранить и показывать канонический `Y1L43`.

**Т-4. Буква категории неизменна.** Переиспользовать букву исчезнувшей категории
под новую нельзя: в поле стоят объекты со старым значением, а по табличке не
видно, в каком году её наносили. Уникальность букв проверять на старте
приложения, а не в рантайме.

**Т-5. `yard_code` — человеческий, не суррогатный** (см. раздел 4).

## 6. Фазы

Порядок обязателен: каждая следующая опирается на предыдущую.

### Фаза A — реестр (основание)

- Модели + миграция `0009_assets.py`.
- Сервис `asset_service.py`: создание с выдачей номера (Т-1, Т-2), смена статуса
  с записью в историю, поиск по номеру с нормализацией (Т-3).
- Импорт 159 объектов из CSV: номер сохраняется как есть (`Y1L43` → `Y1L43`),
  старый идентификатор кладётся в `legacy_id`, счётчики выставляются по максимуму
  из импортированного.
- Справочник дворов: два участка, `code = 1` и `code = 2`.
- Минимальный CRUD в админке (`manager`, `system_admin`).

**Результат:** объекты в БД, номера защищены, данные больше не в CSV.

### Фаза B — связь с заявкой (здесь вся ценность)

- `requests.asset_id` — nullable FK на `assets.id`. Nullable обязательно: заявки
  без объекта (протечка в квартире) никуда не денутся.
- При указании объекта автоматически подставляются: двор, координаты, категория
  заявки по категории объекта (`LAMP` → «Электрика», `BENCH`/`URN`/`GAZEBO` →
  «Благоустройство»). Диспетчеру остаётся описать проблему.
- Выбор объекта в интерфейсе сотрудника: ввод номера с нормализацией + подсказка
  по ближайшим координатам.
- Терминальный статус заявки пишет запись в `asset_status_history` с
  `request_number` (первичный ключ заявки — строковый `request_number`, не id).
- На карточке объекта — список его заявок.

**Результат:** «сломался фонарь `Y1L43`» вместо «около беседки». Реестр начинает
поддерживать себя сам.

### Фаза C — полевой бот пишет в БД

Бот остаётся насовсем, поэтому он должен писать **в ту же базу**, иначе появятся
два источника истины (CSV и таблица), которые неизбежно разъедутся. Бот и БД
`profk_management` живут на одном хосте.

- Замена CSV-хранилища на репозиторий поверх БД; выдача номера — через тот же
  сервис (Т-1, Т-2 в одном месте, а не продублированы).
- Режим повторного обхода: «прошёл мимо `Y1L43`, состояние прежнее» одной кнопкой.
- CSV остаётся только как выгрузка (`/export`).

### Фаза D — карта и аналитика

Слой объектов с фильтрами по категории и состоянию, попап с номером, историей и
заявками. Выгрузка списка номеров по дворам для трафарета. Отчёт «объекты с
наибольшим числом заявок».

## 7. Миграция существующих данных

Источник: `/opt/asset-bot/data/inventory.csv` на profk (160 строк с заголовком).
Колонки: `id, phase, category, status, latitude, longitude, comment, timestamp`.

Соответствие: `phase` → `yard_code`, русское имя категории → код (`Фонарь` →
`LAMP`), `id` → `asset_number` (уже в целевом формате).

Импорт обязан быть идемпотентным (повторный запуск не создаёт дублей — ключ
`asset_number`) и обязан упасть, если после импорта максимальный номер в реестре
больше значения счётчика.

Ожидаемые счётчики после импорта: `1:LAMP = 109`, `1:BENCH = 33`, `1:GAZEBO = 3`,
`1:URN = 9`, `2:LAMP = 10`. Обратите внимание: у `2:LAMP` счётчик 10 при пяти
строках в CSV — номера 6–10 когда-то выдавались, и они не должны выдаваться
заново.

## 8. Доступ

- `manager`, `system_admin` — полный доступ к реестру и справочнику дворов.
- `executor` — чтение объекта и его истории (по номеру из заявки).
- `applicant` (житель) — **не видит модуль**. Решение владельца: номер остаётся
  внутренним инструментом эксплуатации.

## 9. Тесты

Обязательный минимум, повторяющий то, что уже сработало на боте:

1. Номер не выдаётся повторно после удаления объекта и перезапуска приложения.
2. Параллельная выдача двух номеров в одном дворе не даёт коллизии.
3. Нормализация ввода: `y1l043` находит `Y1L43`.
4. Импорт идемпотентен: повторный прогон не плодит дубли.
5. Смена статуса пишет ровно одну запись в историю.
6. Заявка с `asset_id` подставляет категорию и координаты; без него — работает
   как раньше.

## 10. Открытые вопросы

1. **Нужен ли отдельный раздел во фронте** или на первом этапе достаточно выбора
   объекта в форме заявки и карточки объекта? От этого зависит объём фазы B.
2. **Что считать «объектом» дальше.** Сейчас это малые формы двора. Домофоны,
   лифты, детские городки, ограждения — тот же учёт или отдельная сущность с
   паспортом и сроками обслуживания?
3. **Вторая площадка.** Таблицы приедут на .105 вместе с кодом. Нужен ли там
   реестр вообще или он остаётся пустым до отдельного решения?
