# Техническое задание: восстановление функциональности монолитного бота в микросервисной архитектуре

---

## 1. Цели проекта
- Довести Bot Gateway Service и Integration Service до функционального паритета с монолитом `uk_management_bot`.
- Обеспечить пользователям (заявители, исполнители, менеджеры, администраторы) идентичный UX.
- Избежать регрессий: все сценарии монолита должны быть покрыты в новых сервисах.
- Поднять уровень доверия к документации (планы и отчёты должны отражать реальное состояние).

---

## 2. Область работ
- **Bot Gateway** (Aiogram 3.x): все FSM, хэндлеры, клавиатуры и интеграции.
- **Integration Service**: обогащение данными, геокодинг, справочники, кэш, вебхуки.
- **Сервисные клиенты**: Request/User/Shift/Analytics/Integration.
- **Shared**: схемы, общие константы/перечисления для синхронизации между сервисами.
- **Документация и тесты**: обязательное сопровождение.

---

## 3. Источники истины
- `uk_management_bot/handlers/*.py`, `keyboards/*.py`, `states/*.py` — эталон поведения.
- `BOT_MIGRATION_TECHNICAL_SPEC.md` — целевой перечень FSM/клавиатур/обработчиков.
- `SPRINT_19_22_DETAILED_PLAN.md`, `MICROSERVICES_AUDIT_REPORT.md` — ожидания/пробелы.
- Исходники `Integration Service` и `Bot Gateway` — текущая база.

---

## 4. Производственный процесс

### 4.1 Аналитика и декомпозиция
1. Сформировать сводную таблицу “монолит → микросервисы”: хэндлеры, FSM, клавиатуры, зависимости.
2. Отметить, что уже реализовано (по боту) и что отсутствует; оценить пайплайн.
3. Для отсутствующего — подготовить подпроекты (issue/epic), оценить риск/сложность.

### 4.2 Реализация
1. **Bot Gateway**
   - Добавить недостающие FSM (`registration`, `verification`, `onboarding`, `profiles`, `buildings`, `quarterly`, `invites`, `employees`, `expand shifts`).
   - Реализовать хэндлеры-команды/кнопки/коллбэки (≈400).
   - Восстановить клавиатуры (≈900 кнопок); разместить в соответствующих модулях.
   - Построить полноценные интеграции со всеми сервисами (Request, User, Shift, Analytics, Media, Integration).
   - Поддержать мультиязычность (RU/UZ).
   - Добавить middleware для сессий, ролей, авторизации, контекстов.
2. **Integration Service**
   - Исправить геокодинг (auth dependency, геокод/реверс-методы, кэш, health).
   - Реализовать Building Directory API с кэшем и событиями.
   - Финализировать webhook-поток (Stripe, Sheets, Yandex, generic).
   - Ввести платежные и уведомительные интеграции (SMS/Email через Notification Service).
3. **Вспомогательные сервисы**
   - Дополнить Request Service — эндпоинты для building_id, статусов, отчётов.
   - User Service — API для регистрации, онбординга, верификаций, профилей.
   - Shift Service — API для расписаний, передач, планирования, отчётов.
   - Analytics — отчёты под административные панели, WebApp, фильтры.
4. **Документация и тесты**
   - Обновить README, API reference, конфигурации, планы.
   - Диаграммы FSM, клавиатур, команд.
   - Обязательные тесты: юнит, интеграционные (покрытие >80%).

### 4.3 Контроль качества
- Для каждого модуля: checklist “монолит vs новая реализация”.
- Прогон автотестов: `pytest`, нагрузки, линтеры.
- Ручной сценарий проверки по ролевым сценариям.
- Приёмка владельцем продукта.

---

## 5. Интеграции и зависимости

| Контекст | Требование |
|----------|------------|
| Auth/User | API для смены языка, регистрации, верификации, защиты сервисными ключами |
| Request | Обязательные параметры `building_id`, статусы, отчёты, комментарии |
| Shift | Полный стек управления сменами/передачами/планированием |
| Integration | Геокод, справочники, вентиляция данных, кэш, вебхуки |
| Analytics | API для отчётов/метрик бот-панелей, событий для WebApp |
| WebApp | Auth через Bot Gateway, API → Integration → Bot, фронтенд-сборка |
| Notification | Поддержка SMS/Email/WebApp уведомлений |
| Media | Загрузка документов для верификации, приложений к заявкам |
| Мониторинг | Метрики Prometheus, логирование, трассировка |

---

## 6. Требования к тестированию
- Pytest: юнит и интеграционные тесты, покрытие >80%.
- Интеграционные: Bot Gateway ↔ все сервисы (моки/фикстуры).
- Нагрузочные: “миграция монолита” (200+ одновременных пользователей).
- QA чек-листы: регистрация, онбординг, заявки, смены, админ-функции, отчёты.
- E2E-скрипты (Aiogram + API).

---

## 7. Документация
- README каждого сервиса (обновить списки эндпоинтов, FSM/handlers/клавиатуры).
- API спецификации (OpenAPI/JSON Schema).
- FSM-диаграммы/таблицы (Gliffy/Mermaid).
- Руководство по миграции (чек-листы, тест-кейсы).
- Отчёт о соответствии монолиту.

---

## 8. Критерии готовности
1. Bot Gateway/Integration Service закрывают весь функциональный объём монолита.
2. Нет расхождений между документацией и кодом.
3. Живые проверки по всем ролевым сценариям — без ошибок.
4. Coverage ≥80%, линтеры и CI зелёные.
5. Заказчик подтверждает, что миграция завершена.

---

## 9. План и оценки
- Аналитика: 3 дня.
- Bot Gateway (FSM/handlers/клавиатуры/интеграции): 30–35 дней.
- Integration Service доработка: 10–12 дней.
- Вспомогательные сервисы: 12–15 дней.
- Тесты и документация: 10–12 дней.
- Запасы: 10%.

**Итого** ≈ 80–85 человеко-дней.

---

## 10. Риски и меры

| Риск | Уровень | Митигация |
|------|---------|-----------|
| Неточности в документации | Средний | синхронная ревизия, чек-листы |
| Объём клавиатур/кнопок | Высокий | генерация шаблонов, модульные структуры |
| Техдолг → регрессии | Высокий | покрытие тестами, peer review |
| Долгая интеграция сервисов | Средний | выделенный CI-стенд, сервисные ключи |
| Отсутствие WebApp | Высокий | выделить отдельный эпик, фронтенд-команда |

## 11. Завершение
- “Функциональный паритет” принимается по чек-листу.
