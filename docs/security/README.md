# security.txt (RFC 9116) — `PENT-F14`

[`security.txt`](security.txt) в этом каталоге — **артефакт для публикации**, а не
описание. Публикуется **дословно**, без правок на месте: любая правка на хосте
разойдётся с репозиторием, и через полгода никто не скажет, какая версия
настоящая.

## Зачем

До 2026-07-26 `https://profk.uz/.well-known/security.txt` отдавал **`200` с
HTML-страницей** — SPA-заглушку корневого сайта (catch-all
`location / { try_files $uri $uri/ /index.html; }`). Это хуже отсутствия файла:
исследователь получает успешный ответ на security-запрос и парсит из него
мусор вместо контакта. Отдавать `404` было бы честнее, но это принятый риск, а не
исправление — владелец выбрал публикацию настоящего файла.

## Куда публиковать

Только в корень домена: `/.well-known/security.txt` (RFC 9116 §3). Под `/uk/`
кладать бессмысленно — спека требует корень, а `/uk/` обслуживает наш фронт.
Значит это правка **в конфигурации владельца**, а не в этом репозитории;
пошаговая инструкция — [`../audit/2026-07-26-pent-f14-owner-checklist.md`](../audit/2026-07-26-pent-f14-owner-checklist.md).

## Почему один файл на два домена

RFC 9116 §2.5.5 допускает несколько полей `Canonical`. Один файл с двумя
`Canonical` и одинаковым содержимым на обоих доменах — меньше сущностей и нет
шанса, что копии разойдутся. Оба домена в поле `Canonical` присутствуют, поэтому
файл валиден на каждом из них.

## Обязательные поля и срок

`Contact` и `Expires` обязательны по спеке. `Expires` умышленно меньше года
(`2027-07-01`): просроченный `security.txt` по RFC считается недействительным, то
есть файл требует обновления, а не «выставил и забыл».

Чтобы срок не протухал молча, есть гейт: `tests/services/test_security_txt.py`
падает **за 30 дней до** `Expires` с инструкцией продлить. Красный тест здесь —
не поломка, а напоминание в единственный момент, когда оно нужно.
