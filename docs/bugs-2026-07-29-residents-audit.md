# Аудит раздела «Жители» — работоспособность и безопасность (profk, 2026-07-29)

Разбор раскатанного модуля (PR #285–#294) и двух фиксов поиска (#295, #296)
после того, как они отработали в проде. Проверка шла по коду и по живому
инстансу; всё, что ниже, либо доказано на проде, либо явно помечено как
непроверенное.

Закрыто в PR #297, #298, #299, #300 — все раскатаны на profk 2026-07-29.
Список LOW внизу не закрыт и ждёт решения.

---

## HIGH-1. Токен бота попадал в логи через текст исключения httpx

**Где.** `api/residents/documents.py` (прокси документов) и предсуществующий
`api/shifts/router.py` (`getMe` при выдаче инвайт-ссылки).

**Суть.** Утечка шла не через наш f-string, а через **текст исключения**:
после `raise_for_status()` httpx кладёт в сообщение полный URL запроса, а URL
Bot API содержит токен целиком. Проверено в живом контейнере API:

```
str(e) = Server error '500 Internal Server Error' for url
         'https://api.telegram.org/bot<ТОКЕН>/getFile?file_id=X'
```

Срабатывало на любом ответе Telegram, кроме 2xx и явно обработанного 400 — то
есть на **429 (rate limit)**, 401 после ротации токена и 5xx. Токен бота даёт
чтение всех апдейтов, отправку от имени бота и скачивание любого файла,
который бот видел.

**Фактической утечки не было**: в сохранённых логах прода 0 строк с токеном.

**Почему существующая защита не сработала.** `SecurityFilter` в проекте есть и
активен на проде (`DEBUG=False`), но его паттерн `(Bot\s+)\d+:[A-Za-z0-9_-]+`
требует пробела после «Bot», а в URL пробела нет. Проверено прогоном фильтра
прямо на проде — строка возвращалась нетронутой.

**Как починено (PR #297).** Два слоя: call-site'ы логируют класс исключения и
HTTP-статус через `utils/http_errors.describe_http_error`, но не само
исключение; `SecurityFilter` получил `REDACT_WHOLE_PATTERNS` с заменой
URL-формы **целиком** (общий `_redact_match` вырезал бы только хвост после
первого двоеточия, оставив id бота открытым).

**Прод-проверка.** Обе формы URL (`/bot…` и `/file/bot…`) → `/bot[REDACTED]`;
`describe_http_error` на 429 → `HTTPStatusError (HTTP 429)`; в логах api и
бота 0 строк с токеном.

## MEDIUM-1. Ни одного рейт-лимита в разделе

**Суть.** Конвенция проекта — лимит объявляется на маршруте (`@limiter.limit`),
общего `default_limits` у лимитера нет: маршрут без декоратора не ограничен
вовсе. 26 маршрутов других доменов лимит несут, а все **16** маршрутов
«Жителей» уехали в прод без единого.

Чем это опасно: прокси документов ходит во внешний Telegram и буферизует до
20 МБ в память на запрос, а approve/reject/request-documents на каждый вызов
отправляют жителю сообщение в Telegram — чужой чат можно завалить.

**Чего лимит НЕ даёт.** Auth-зависимости FastAPI выполняются **до** лимитера,
поэтому неаутентифицированный трафик до счётчика не доходит. Это защита от
злоупотребления авторизованной сессией менеджера, а не от анонимного флуда.

**Как починено (PR #298).** Чтения 60/мин, прокси файла 30/мин, мутации
30/мин, порождающие уведомление 20/мин. Снапшот OpenAPI не сдвинулся:
`request: Request` FastAPI в схему не выносит (сверено `--check`).

**Прод-проверка.** Серия по прокси документов: ровно 30 прошли, 31-й → 429;
у каждого маршрута свой счётчик, раздел продолжает работать.

## MEDIUM-2. Зачистка документов тихо не происходила

**Суть.** `delete_user_documents_from_media_service` возвращала `True` в том
числе когда Media Service **недоступен** («считаем успешным») и когда
удалилась лишь **часть** файлов. Строки `UserDocument` к моменту вызова уже
удалены одной транзакцией, то есть сканы паспортов остаются в Media Service и
Telegram, а из карточки исчезают — и ни следа в логах. Легаси-путь бота вдобавок
писал утвердительное «документы удалены» безусловно.

**Как починено (PR #299).** Функция возвращает `MediaCleanupResult`
(`deleted` / `nothing_to_delete` / `partial` / `unavailable` / `failed`).
Истинность совместима с прежним `if await …`, но честна: истинны только
исходы, после которых чистить нечего. Оба вызывающих логируют WARNING с
`telegram_id` — это ручка для повторного запуска зачистки.

⚠ **В проде не проверялось.** Ветка «сервис недоступен» покрыта тестом; ронять
Media Service ради проверки не стали. Проверено только то, что успешный путь
верификации не изменился.

## MEDIUM-3. `approve_account` без guard'а Т2

**Суть.** У `block`/`unblock` guard есть, у `approve` не было. «Сотрудники»
активируют через `activate_employee`, который делает **три** вещи: `status`,
`verification_status` и **поднимает `active_role`** до стафф-роли. Здешний путь
делал только первую.

В докстринге самого `activate_employee` написано зачем: приглашённый через бота
сотрудник после `/join` остаётся с `active_role='applicant'`, и без подъёма у
него не появится меню менеджера в боте. Такой аккаунт — `applicant` + стафф-роль
в статусе `pending` — **попадает в список жителей**, и кнопка «Одобрить» там
показывалась. То есть раздел воспроизводил ровно тот баг, ради которого
`activate_employee` и написан.

**Как починено (PR #299 + #300).** `_ensure_pure_applicant` вызывается и на
одобрении, **до** проверки статуса (иначе стафф видел бы «уже одобрен» и не
понимал, что раздел не его). Кнопка на фронте скрыта тем же признаком, что и
блокировка.

**Дефект, внесённый самой правкой (#300).** Guard стал общим, а его текст
остался от блокировки: на кнопке «Одобрить» пользователь получал «блокируйте
его из раздела Сотрудники» — бессмыслица, уводящая от настоящего действия.
Найдено прод-проверкой сразу после выкатки #299; тесты пропустили, потому что
проверяли только наличие слова «Сотрудники». Текст переписан нейтрально к
операции, тест теперь пинит отсутствие «блокируйте» на пути одобрения.

**Прод-проверка.** Временная стафф-роль тестовому жителю → `approve` и `block`
оба дают 409 с нейтральным текстом; карточка в браузере: с чистой ролью видны
«Одобрить аккаунт» и «Заблокировать», с ролью `executor` — ни одной кнопки и
поясняющая подпись. Роль и статус откачены, записей аудита не прибавилось.

## Проверено, претензий нет

| Что | Как проверено |
|---|---|
| Аутентификация на всех маршрутах | живой прод без cookie → 401 (405 на неверный метод) |
| RBAC manager-only | `require_roles("manager")` на каждом маршруте |
| IDOR по привязкам | на живых данных: каждый существующий `ua_id` от чужого жителя → 404 |
| Скоуп «кто такой житель» | по каждому юзеру прода: чистые менеджеры и soft-deleted недоступны |
| `file_id` наружу | отсутствует в схеме, единственный путь к файлу — прокси |
| CSRF | cookie httpOnly + Secure + SameSite=Strict |
| WebSocket | Origin-гейт до `accept()`, проверка роли, пересверка личности раз в 60с |
| Прокси документов | буфер до заголовков, `nosniff`, `attachment` для не-картинок, sniff по магическим байтам, 415/404/502/413 |
| SSRF | `file_path` приходит от Telegram, хост зафиксирован |
| Публичность OpenAPI | `/uk/docs` и `/uk/openapi.json` отдают **200, но это SPA**: edge проксирует только `/uk/api/`. Схема API не опубликована — различено по телу и content-type, не по коду ответа |

## Открыто (LOW) — ждёт решения

1. `_binding_out` кидает `AssertionError` → 500 при конкурентном удалении
   привязки; должно быть 404/409.
2. Нет верхней границы длины списка `document_types`.
3. Эндпоинты верификации без guard'а Т2: менеджер может переключить ось
   верификации у сотрудника. Доступ это нигде не гейтит — эффект косметический.
4. Имя файла для скачивания берётся из данных жителя (содержимое при этом
   проверено по магическим байтам).
5. AST-гейт `.ilike(` не сканирует `media_service/` — там 4 сознательно не
   тронутых места; новый поиск в этом сервисе гейт не поймает.
6. Расхождение сворачивания регистра: колонка — ICU в PostgreSQL, шаблон —
   питоновский `str.lower()`. Для RU/EN совпадают.
7. Системное лечение локали `C` — пересоздание кластера в UTF-8
   (`initdb --locale`), dump/restore с даунтаймом.
