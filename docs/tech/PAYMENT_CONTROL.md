# Контроль платежей и связь с квартирой

Реализовано 2026-09-05. Отдельный FastAPI-сервис `payment_control/` со своей БД
и разделом дашборда `/uk/dashboard/payment-control`. Браузер обращается через
авторизованный UK API; сервисный ключ остаётся на сервере. Самостоятельного
публичного входа нет: используется авторизация УК.

## Возможности

- CSV/XLSX: предпросмотр, проверка всех строк, история, явная активация.
- Снимки задолженности и предоплаты в UZS; отдельно — реестры платежей.
- Просмотр по 200 строк, ошибки и журнал действий с пользователем и причиной.
- Повтор того же содержимого с теми же метаданными возвращает прежний импорт.
- Уникальность активной операции по источнику и ID, включая конкурентную
  активацию. При пересечении реестров отклоняется весь новый пакет: исключите
  уже загруженные операции и загрузите исправленный файл.
- Деактивация с причиной, сохранение истории и повторная активация.
- `Apartment.account_number`: текст до 64 символов, начальные нули сохраняются;
  пустая строка очищает связь. Уникален в инсталляции УК, включая неактивные
  квартиры. Автоматического переноса связи между квартирами нет. Алфавит —
  только латиница, цифры, точка и дефис: кириллица запрещена, иначе гомоглифы
  («О» против «O») дают два визуально одинаковых, но разных счёта. При конфликте
  ответ 409 называет квартиру-держателя и её адрес; неверный формат — 422.
- Массовое создание квартир (`/apartments/bulk`) лицевые счёта НЕ переносит:
  диапазон номеров квартир не совпадает с номерами счетов. Заполняются точечно
  в форме квартиры.
- Карточка квартиры: долг, предоплата, дата, источник, имя файла и ссылка на
  тот же счёт и страницу исходной строки в новом разделе.
- Доступ к финансовому модулю: `manager` и `admin`, только `approved`.
  Публичное табло, жители и исполнители доступа не получают.
- Интерфейс RU/UZ, общая реализация для InfraSafe и PROFK.

## Правила актуальности

Текущая запись выбирается для конкретного счёта среди активных снимков по
`as_of DESC, import_id DESC`. При одинаковой дате более поздно загруженное
исправление имеет приоритет. Поздняя активация старого файла не перекрывает
более свежую дату. Дата загрузки не заменяет дату состояния.

Отсутствие строки в следующем файле не обнуляет баланс: остаётся прежняя
активная запись с её датой. Подтверждённый ноль — явная строка с `debt=0` и
`prepayment=0`. После деактивации показывается предыдущая активная запись
либо «нет активных данных».

`no_account`, `no_data`, `available`, `unavailable` — разные состояния.
Недоступность сервиса не преобразуется в ноль. Карточка запрашивает суммы при
открытии, возвращении фокуса и раз в минуту, пока открыта. Раздел обновляется
после своих операций и кнопкой «Обновить».

Платежи упорядочены по дате самого платежа (`paid_at DESC, id DESC`), а не по
дате пакета: свежий платёж из старой выгрузки не отрезается лимитом 200.

Платежи не вычитаются из снимков: выгрузка задолженности уже может их учитывать.
Они видны отдельно для сверки. Нет начислений, автоматической разноски,
возвратов денег, платёжного шлюза, статуса просрочки без срока оплаты или
фонового получения банковских файлов.

## Форматы

Примеры: `payment_control/examples/balances.csv` и `payments.csv`.

```csv
account_number;debt;prepayment
001;120000.00;0.00
002;0.00;50000.00
003;0.00;0.00
```

```csv
account_number;operation_id;paid_at;amount
001;bank-unique-id;2026-09-01;20000.00
```

В XLSX — те же заголовки первой строки активного листа. Лицевой счёт должен
быть текстовой ячейкой: числовые ячейки отклоняются, поскольку Excel уже мог
удалить начальные нули. Формулы в суммах отклоняются. Даты: YYYY-MM-DD,
DD.MM.YYYY или дата Excel. Суммы неотрицательные, до двух десятичных знаков;
сумма платежа строго положительна. Долг и предоплата хранятся раздельно.
Колонки `debt` и `prepayment` обязательны; отсутствие суммы обозначается нулём.
Необязательная колонка `note` — свободный текст до 500 символов, управляющие
символы вычищаются. `operation_id` отклоняется, если начинается с `=`, `+`, `@`
или `-` (Excel трактует это как формулу). Данные раздела никуда не
экспортируются в табличные форматы; если такой экспорт появится, ведущие
формульные символы обязан экранировать экспортёр. Поддержаны русские заголовки
«Лицевой счёт» (а также «л/с»), «Долг» («Задолженность»), «Предоплата»
(«Переплата»), «Номер платежа», «Дата платежа», «Сумма», «Примечание».

CSV: UTF-8/BOM или Windows-1251, разделитель `;` или `,`. Лимиты: 5 МБ файла,
30 МБ распакованного XLSX, 10 000 строк, 30 колонок. При ошибке любой строки
активация запрещена. Хранятся исходные значения ячеек, нормализованные строки,
имя файла и журнал действий; оригинальный бинарный файл не архивируется.

Источник — стабильный идентификатор: не меняйте имя банка/расчётной системы
между загрузками, иначе для дедупликации это другой источник. Одна инсталляция
сервиса обслуживает один расчётный контур УК. Разные услуги/валюты нельзя
загружать как общий баланс одного счёта: их консолидация не реализована.
История счёта ограничена 50 активными снимками и 200 платежами; остальные
данные доступны через историю импортов.

## Подключение

Overlay `docker-compose.payments.yml` добавляет `payment-postgres` (PostgreSQL
16), `payment-migrate`, `payment-api`. Порты новой БД и сервиса наружу не
публикуются. Внутренний адрес: `http://payment-api.internal:8101/v1`.
Если edge применяет allowlist, разрешить `/uk/api/v2/payment-control/*`
на основной UK API. Не открывать `/v1` напрямую. Префикс заявлен в
`docs/audit/2026-06-07-infrasafe-edge-allowlist-contract.md` как ожидающий
добавления: до подтверждения InfraSafe раздел отдаёт 404 на обеих площадках.

Пункт меню закрыт build-флагом фронта `VITE_PAYMENTS_ENABLED` (по умолчанию
выключен). Включать только там, где overlay поднят, `PAYMENT_SERVICE_TOKEN`
задан и префикс заявлен на edge — иначе менеджер видит раздел, который целиком
отвечает 404/503.

Ограничения частоты на стороне UK API: загрузка предпросмотра 10/мин,
активация и деактивация 30/мин на пользователя.

Секреты в Doppler для каждого окружения:

- `PAYMENT_SERVICE_TOKEN`: случайный ключ не короче 32 символов;
- `PAYMENT_OWNER_PASSWORD`: владелец отдельной БД и миграции;
- `PAYMENT_APP_PASSWORD`: runtime-роль с DML и без DDL.

К штатным compose-файлам бренда добавить `-f docker-compose.payments.yml`.
Все команды запуска выполняются через `doppler run` по регламенту uk-deploy.

1. Собрать `api access-api app migrate frontend payment-api payment-migrate`.
2. Поднять только новую `payment-postgres`, дождаться healthy. Скрипт
   `payment_control/provision.sql` создаёт ограниченную роль при инициализации
   пустого тома: там только независимое от таблиц — роль, пароль, `CONNECT`,
   `USAGE` и default-права «читать и дописывать» (таблиц на этот момент ещё нет).
   Точные `UPDATE` для `payment_imports` и `DELETE` для `payment_claims` выдаёт
   миграция `payment_001` сразу после создания таблиц, поэтому шаг 4 обязателен
   не только для схемы, но и для прав. Для ротации пароля повторить скрипт через
   psql, предварительно передав обновлённый `PAYMENT_APP_PASSWORD` контейнеру БД.
3. Выполнить основную миграцию `migrate`: ревизия `016` добавляет лицевой счёт.
   После изменения схемы обязательны согласованная пересборка и перезапуск
   всех `api/access-api/app`, как описано в uk-deploy.
4. Выполнить `run --rm payment-migrate`, затем
   `run --rm payment-migrate alembic -c payment_control/alembic.ini check`.
5. Поднять `payment-api`; проверить `/health` внутри контейнера.
6. Перезапустить собранные runtime-сервисы УК и фронт по штатному регламенту.
7. Проверить предпросмотр, активацию, карточку квартиры и ссылку на тестовом счёте.

Для обновления существующие БД не пересоздавать: сначала миграции, затем runtime.
В этой задаче рабочий/production-деплой не выполнялся.

Обязательный операционный чек-лист до включения флага (вне этого репозитория):

1. Внести `payment-postgres` и `payment-api` в `expected-containers.tsv` и
   `inventory.yml` на profk-obs — иначе мониторинг даст P2 через 30 минут.
2. Добавить БД `payment_control` в кросс-бэкап хостов, как ранее `uk_media`, и
   прогнать проверку восстановления (`pg_restore -l`). Том `payment_pg_data`
   включить в резервное копирование.
3. Подтвердить у InfraSafe добавление префикса `/api/v2/payment-control` в
   edge-allowlist на обеих площадках.
4. Только после этого собирать фронт с `VITE_PAYMENTS_ENABLED=true`.

## Осознанные ограничения

- Тексты ошибок проверки файла и лицевого счёта приходят от бэкенда только
  по-русски; интерфейс переведён на RU/UZ, а сообщения валидации — нет.
  Машинных кодов ошибок не введено: они потребовали бы отдельного каталога на
  фронте. Для узбекоязычного менеджера это известное ограничение раздела.
- Деньги хранятся строками `Decimal` внутри JSON-строки импорта (не NUMERIC-
  колонками): единственная точка записи — `payment_control/app.py`, БД валидность
  суммы не сторожит. Тип `JSON` (не `JSONB`) выбран ради переносимости на sqlite,
  на котором гоняются тесты и CI сервиса; JSON-предикатов по данным нет.
- Пагинация истории импортов — `LIMIT/OFFSET` по 50. На заявленном масштабе
  (ежедневные выгрузки) достаточно; курсорная пагинация — вопрос отдельной задачи.
- Деактивация неактивного импорта отвечает 409, а не «тихим успехом».

## Проверки

```bash
.venv/bin/python -m pytest payment_control/tests --cov=payment_control --cov-fail-under=80
.venv/bin/python -m pytest tests/api/test_payment_control.py tests/api/test_addresses.py
npm --prefix frontend test
npm --prefix frontend run build
npm --prefix frontend run build:profk
make test-ci
```

CI `.github/workflows/payment-control.yml` проверяет новый сервис и миграции.
Основной CI проверяет миграцию квартиры, gateway и фронтенд.
Браузерный сценарий с реальными API и одноразовыми SQLite-БД:

```bash
cd tests/e2e
npx playwright test --config payment-control.config.ts
```

Нужны `.venv` с зависимостями проекта/сервиса, зависимости фронтенда и Chromium
Playwright. Серверы теста слушают только loopback на 18085 и 5179. Только в
тестовом хосте авторизация заменена тестовым менеджером; production-аутентификация
не меняется.
