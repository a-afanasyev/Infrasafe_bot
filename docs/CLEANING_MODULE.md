# Модуль «Уборка» (контроль уборки подъездов)

> _Последнее редактирование: 2026-11-16. Состояние: этапы 1–5 реализованы; модуль включён на обеих площадках._

План уборки на дом, привязка уборщиц к подъездам, фото каждого этажа из Mini App в день уборки,
автоприёмка с выносом спорного менеджеру, жалобы жителей, табель, «уборка сегодня» для жителей.

## Что система гарантирует

Клиент недоверенный: время съёмки и сам кадр приходят с телефона. Система **не доказывает**, что
подъезд убран и что снимок сделан сейчас. Она делает повторное использование старого фото трудным
и отправляет подозрительное человеку. Решения опираются на серверные факты.

| Уровень фото | Серверный факт | Автоприёмка |
|---|---|---|
| `live` | задание открыто онлайн, фото получено в окне сессии (120 мин) | да |
| `deferred` | сессия была, фото получено позже окна, до конца дня | нет (настройка) |
| `offline` | сессии не было, либо кадр с системной камеры | нет |
| `late` | получено после конца дня, не позже 24 ч | доказательство для ручного зачёта |

Уровень `live` — подсказка, а не гарантия: признак «кадр с камеры приложения» присылает клиент, и тот, кто
шлёт запросы в обход приложения, может выдать старый снимок за живой в окне сессии. Против этого остаются
сходство кадров, «слишком быстро», испытательный срок и выборка.

Житель может пожаловаться не более чем на 3 подъезда в день. Открытое фото отдаётся только за сегодня.

Уже скачанное жителем фото отозвать нельзя: скрытие действует на следующие запросы.

## Включение

- `CLEANING_ENABLED` (бот и API, compose: `app` и `api`) — по умолчанию выключен. Без него:
  `/api/v2/cleaning/*` и открытые дом/фото отвечают 404, сводка `today` — пустым 200 (табло в холле
  опрашивает постоянно), блок `cleaning` вырезан из страницы жителей, тик планировщика не
  зарегистрирован, фото в чате от уборщицы обрабатывается как раньше.
- `VITE_CLEANING_ENABLED` (build-arg фронта) — пункт меню, страницы дашборда, блок и раздел жителей.
- Порядок выкатки: **медиа-сервис** (категория `cleaning_photo`) → `migrate` (034) → API и бот → фронт.
- `/api/v2/cleaning` заявить в edge-allowlist обеих площадок до включения. Открытые маршруты живут
  под уже разрешённым `/api/v2/public`.
- Права: `cleaning.read` / `cleaning.manage` — менеджер; `cleaning.work` — исполнитель. Уборщица =
  право `cleaning.work` + специализация `cleaning`.

## Данные (миграция 034)

| Таблица | Назначение |
|---|---|
| `cleaning_plan_versions` | неизменяемые версии плана дома с датами действия и снимком этажности |
| `cleaning_assignments` | ответственный за подъезд на период |
| `cleaning_building_settings` | показ жителям (на задания не влияет) |
| `cleaning_rules` | append-only версии настроек; на дату действует версия, созданная до её начала |
| `cleaning_days` | маркер генерации/закрытия дня, снимок конца дня, отметки отправки сообщений бота |
| `cleaning_tasks` | задание на (дом, подъезд, дата): снимок работ, точек съёмки, ответственного |
| `cleaning_photos` | операции загрузки с сохранённым исходом; текущее фото точки — `is_current` |
| `cleaning_task_events` | журнал переходов и решений |
| `cleaning_complaints` | жалоба жителя, связанная с заданием; номер заявки дописывается позже |

Точка съёмки — строка `slot`: `floor:3` (этаж) или `point:elevator`. **«−1 этаж» — этаж плана**
(решение владельца 2026-11-16): отрезок этажей может начинаться с −1, в редакторе есть вариант
«Только −1 этаж», слот `floor:-1`. Нулевого этажа нет; «все этажи» — только надземные, в норму
покрытия −1 не входит. «Выход на парковку» — работа плана `parking` со своими днями недели и
подъездами (точка `point:parking`, в норму этажей не входит). Этаж помыт ⟺ у его слота есть
текущее фото. **Первый этаж снимается тремя точками** вместо кадра `floor:1`: `point:entry1`,
`point:entry2`, `point:lift_hall` (`planning.FIRST_FLOOR_POINTS`, подмена при генерации задания —
`planning.shooting_slots`). План, покрытие и нагрузка считают первый этаж одним этажом.

## Правила, которые легко сломать

- **Правка плана, привязки и настроек действует с завтра.** Генерация дня берёт версии,
  действовавшие на эту дату (`days.ensure_tasks`), результат не зависит от момента запуска.
- **Конец дня задаёт менеджер** (`day_end_time`, по умолчанию 23:59). День закрывается через 5 минут
  после него: незавершённое → `expired`, не начатое → `missed`.
- **Статус меняется только через `transitions.move`** под блокировкой строки задания.
- **Одна операция загрузки = один ключ** (`uploads.upload_photo`): повтор возвращает сохранённый
  исход; принадлежность и содержимое сверяются всегда, срок и статус при повторе — нет.
- **Финализация блокирует задание заново**: фото активируется, только если ответственный тот же и
  задание открыто; иначе сохраняется доказательством.
- **Пересъёмка:** текущим становится кадр с большим временем съёмки, а не финализированный позже.
- **Решение менеджера идёт с версией задания** (`control.decide`): расхождение — отказ `stale`.
- **Жалоба переводит принятое задание на проверку в одной транзакции** (`complaints.file_complaint`),
  независимо от создания заявки. На задании в любом другом статусе жалоба поднимает `version` —
  решение менеджера по карточке, открытой до жалобы, получит `stale`.
- **Временный сбой медиа-сервиса исходом не считается**: аренда сбрасывается, строка остаётся
  `pending`, чистка не трогает операции моложе суток. Окончательный отказ медиа (`media_rejected`)
  сохраняется как `bad_photo`.
- **Покрытие этажей считается по худшему подъезду**: строка «только подъезд 1» не закрывает подъезд 2.
- **Очередь проверки и жалобы на дашборде — за 60 дней**, а не за просматриваемую неделю.
- **Автоприёмка (`acceptance.evaluate`) только отправляет на проверку** — отклонить сама не может.
  Причины: фото вне окна сессии, повтор кадра, почти тот же кадр того же этажа, слишком быстро,
  жалоба, испытательный срок, выборка.
- **Миниатюры — превью, оригинал — по нажатию.** Все три маршрута фото отдают уменьшенный JPEG из
  кэша медиа-сервиса, оригинал — с `?original=true`. Превью прогревается сразу после загрузки кадра.
  Без этого сетка из десяти фото качала десять оригиналов из Telegram и ловила 504 на edge.
- **Какие фото видят жители** (при включённом показе фото у дома, только за сегодня и только у
  принятого задания): на странице-обзоре `/cleaning` — все текущие фото подъезда; в приложении
  жителя — одно фото подъезда (первая точка первого этажа либо нижний снятый этаж) и лифт, если его мыли.
- **Жалоба жителя создаёт заявку сразу на уборщицу этого подъезда** (`preferred_executor_id` в
  `persist_request` → `dispatch`): без подбора дежурного и независимо от автоназначения. Если у
  подъезда нет ответственного или задания — обычная диспетчеризация категории «Уборка».
- **Жители видят «убрано» только у принятого задания**; на проверке, отклонённое и незавершённое
  для них одинаково «ещё не убрано». Имён сотрудников в открытых ответах нет.

## API (`/api/v2/cleaning`)

| Кому | Маршруты |
|---|---|
| Менеджер, план | `GET /buildings`, `GET/PUT /buildings/{id}/plan`, `PUT /buildings/{id}/settings`, `PUT /assignments`, `GET /staff`, `GET/PUT /rules` |
| Менеджер, контроль | `GET /control/tasks`, `GET /control/tasks/{id}`, `POST /control/tasks/{id}/decision`, `PUT /control/tasks/{id}/responsible`, `GET /control/photos/{id}/file`, `GET /control/complaints`, `POST /control/complaints/{id}/decision`, `GET /control/timesheet` |
| Уборщица | `GET /my/tasks`, `POST /tasks/{id}/session`, `POST /tasks/{id}/photos`, `GET /tasks/{id}/photos/{photo_id}/file` |
| Житель | `POST /complaints` (только свой дом) |
| Открыто | `GET /api/v2/public/cleaning/today`, `/buildings/{id}`, `/photos/{id}` |

## Интерфейсы

- **Дашборд** (`frontend/src/pages/cleaning/`): план дома, уборщицы и нагрузка, контроль (матрица
  план/факт, очередь, жалобы, табель, настройки), карточка задания.
- **Уборщица** (`frontend/src/twa/cleaning/`): одна страница на оба режима Mini App
  (`/twa/exec/cleaning`, `/twa/s/cleaning`), вход — плитка на экране смены. Камера в приложении,
  очередь кадров в IndexedDB.
- **Жители:** блок «Уборка» на `/home` (счёт по домам), открытый обзор по всем домам `/cleaning`
  (статусы подъездов и фото), раздел `/twa/app/cleaning` в приложении.
- **Бот** (`services/cleaning/notify.py`): утром — сколько подъездов, перед концом дня — что не
  завершено, после закрытия дня — итог менеджерам. Фото уборки в чате не принимаются.

## Известные упрощения и чего нет

- **Камера и связь на реальных телефонах не проверялись.** Живая камера в Telegram WebView и доля
  фото уровня `live` в подъездах — первое, что нужно проверить на пилоте: от этого зависит, сколько
  визитов автоприёмка снимет с менеджера.
- Штамп на фото — латиницей (дата, № задания, точка, уровень доверия): во встроенном шрифте Pillow
  нет кириллицы.
- Файлы-сироты в медиа-сервисе отдельно не ищутся (см. `cleanup.py`).
- Заявка по жалобе досоздаётся повторным запросом жителя, а не фоновым тиком; жалоба без заявки
  видна менеджеру, задание при этом уже на проверке.
- В приложении жителя «мой подъезд» не выделяется: API адресов жителя не отдаёт номер подъезда.
- Строки «уборка сегодня» на табло в холле (ТВ-режим) нет — только блок на странице жителей.
- Отдельного оповещения менеджеру о каждом спорном задании нет — очередь в дашборде и итог дня.
- ИИ-проверка фото (этап 6) не делалась — отдельным решением.
- Чужой исполнитель (не ответственный) при загрузке получает отказ `not_yours`, который пишется в
  карточку задания; гонка двух первых сохранений показа дома даёт 500; соединение IndexedDB очереди
  не закрывается явно — низкие находки ревью, оставлены.
- Замена ответственного в день уборки не открывает новое окно сессии: кадры замены идут как
  `deferred`, задание уходит на проверку.
- Гость на `/home` пожаловаться не может (нужен вход); показ дома жителям сохраняется вместе с планом;
  закрытие дня зависит от тика бота (ленивого закрытия из API нет).
- Табель выгружается в CSV из браузера (месяц понедельника выбранной недели), серверного отчёта нет.
- План — дни недели; работы реже раза в неделю не поддержаны. Конец дня — одно время на компанию.
