# Баги, найденные прод-проверкой раздела «Жители» (profk, 2026-07-28)

Оба найдены при ручной проверке нового раздела в проде. Оба **шире раздела**:
затрагивают и уже существующие экраны. Ниже — что именно сломано, чем доказано
и что с этим сделано.

---

## BUG-1. Поиск не находит кириллицу: кластер БД создан в локали `C`

**Симптом.** `GET /api/v2/residents?q=Админ` → 1 результат, `?q=админ` → 0.
Латиница при этом ищется в любом регистре (`nazya` = `NAZYA` = 1).

**Причина — не в коде, а в кластере.** На profk:

```
profk_management=# SHOW lc_ctype;   → C
profk_management=# SELECT lower('АДМИН');            → АДМИН
profk_management=# SELECT 'Администратор' ILIKE '%админ%';  → f
```

В локали `C` `lower()` и `ILIKE` сворачивают регистр **только для ASCII**.
Система русскоязычная, поэтому «поиск по ФИО» без кириллицы — нерабочая функция.

**Область поражения шире раздела «Жители».** Тот же дефект у всех `ilike`-поисков
по пользовательским строкам:

| Место | Что ищется |
|---|---|
| `api/shifts/service.py:list_employees` | ФИО и телефон сотрудников (страница «Сотрудники») |
| `services/addresses/queries.py:search_apartments` | адреса и номера квартир |
| `api/materials/router.py` | наименования материалов |
| `api/callcenter/router.py` | поиск по звонкам |

**Что сделано.** Починен **только** раздел «Жители» (`services/residents/queries.py:_ci_contains`):
на PostgreSQL сравнение идёт как `lower(колонка COLLATE "und-x-icu") LIKE lower(шаблон)`.
ICU-коллация есть в `postgres:15` из коробки — ни миграции, ни расширения не нужны.
Проверено на живой БД profk: `lower('АДМИН' COLLATE "und-x-icu")` → `админ`,
и `lower(first_name COLLATE "und-x-icu") LIKE '%админ%'` находит «Администратор».

**Что НЕ сделано (осознанно, ждёт решения владельца).**

1. Остальные четыре поиска из таблицы выше не тронуты — это правка чужих доменов
   за пределами задачи.
2. Системное лечение — пересоздать кластер в локали `C.UTF-8`/`ru_RU.UTF-8`
   (`initdb --locale`), тогда обычный `ILIKE` заработает везде и точечные
   ICU-коллации станут не нужны. Это **downtime + dump/restore**, отдельная
   операция. Пока не сделано, каждый новый поиск в коде обязан использовать
   ICU-коллацию, иначе тихо не найдёт русские имена.

⚠ **Тестами это не ловится.** Сьют `tests/api` гоняется на sqlite, где `ILIKE`
эмулируется питоновским слоем SQLAlchemy и кириллицу сворачивает. Поэтому в
`tests/api/test_residents_search_collation.py` проверяется не только поведение,
но и **форма скомпилированного SQL** под диалект postgresql.

## BUG-2. Поле поиска в топбаре теряет символы

**Симптом.** В поле поиска топбара набираешь «админ» — в поле оказывается «амн».
При медленном вводе (пауза между клавишами) не остаётся вообще ничего.
Воспроизведено и на **уже существующей** странице «Сотрудники» — то есть дефект
предсуществующий, не регресс нового раздела.

**Замер в живом браузере** (profk, DevTools):

```js
// сразу после события input
{ value: "",  focused: true, sameNode: true }
// через 400 мс
{ value: "А", focused: true, sameNode: true }
```

Узел поля не пересоздаётся и фокус не теряется — **откатывается значение**.

**Причина.** Страница отдаёт узел поля в топбар не напрямую, а через состояние
контекста `useTopbar`, которое обновляется в `useEffect` — то есть **вторым
коммитом**. У контролируемого поля (`value={search}`) React в фазе обработки
события сверяет DOM-значение с последним отрендеренным `value` (всё ещё старым)
и откатывает DOM. Следующее нажатие попадает в это окно — символ теряется.

**Что сделано.** В разделе «Жители» поле переведено на неконтролируемое
(`defaultValue` + `debounce 300мс`), а его узел мемоизирован **без** зависимости
от `search`. Побочно снят и второй дефект — запрос на каждое нажатие клавиши.

**Что НЕ сделано.** Страницы «Сотрудники» и «Адреса» с тем же паттерном не
тронуты. Системное лечение — держать состояние поиска в самом топбаре, а
страницам отдавать только колбэк; это переделка `TopbarContext` и всех его
потребителей, отдельная задача.
