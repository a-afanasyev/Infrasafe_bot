# BUG-189 — фото заявки не грузится в дашборде (profk, 260909-001) — 2026-09-09

Репорт владельца: «у заявки 260909-001 не грузится фото». Заявка на profk,
категория `elevator`, создана 07:22 UTC из колл-центра, одно фото (media id 103)
приложено менеджером через дашборд в 07:23 и тогда же успешно показано.

## Что произошло (по логам profk, все времена UTC)

| Время | Слой | Событие |
|---|---|---|
| 09:59:19.033 | media-service | `GET /api/v1/media/103/file` → `download_file` → соединение с `api.telegram.org` повисло |
| 09:59:48.98 | edge nginx | `upstream timed out (110) while reading response header` → браузеру **504** (`proxy_read_timeout` edge = 30 с) |
| 10:00:19.035 | API | `media STREAM … transport error (attempt 1/3), retry in 0.5s` — свой таймаут 60 с истёк |
| 10:00:19.439 | media-service | `download_file …: попытка 1 не удалась: ConnectTimeout` — ровно 60 с |
| 10:00:20.36–20.63 | media-service | обе попытки (ретрай media-service и ретрай API) скачали файл с Telegram за ~1 с |
| 10:00:20.866 | media-service | `Response: 200 - 61.833s` — ответ ушёл в никуда, клиента уже нет |

Повторная проба 10:01 UTC из контейнера `uk-management-api` напрямую в media-service:
`200 image/jpeg 111190 байт за 1.29 с`. Файл цел, сбой транзиентный.

Частота за 14 дней логов media-service: **2 случая** с одинаковой подписью
(2026-09-02 07:20 → `Response: 200 - 61.630s`, 2026-09-09 10:00 → `61.833s`).
Каждый случай = сломанная картинка у того, кто в этот момент открыл заявку.

## Корневая причина

Таймауты по цепочке не согласованы с бюджетом edge (30 с), поэтому один
транзиентный connect-stall до Telegram превращается в 504 для браузера, хотя
ретрай через полсекунды успешен:

1. **`media_service/app/services/telegram_client.py:172`** —
   `httpx.AsyncClient(timeout=60)`: одно число на connect/read/write/pool.
   Повисшее соединение ждётся 60 с, ретраи (`0, 0.5, 1.5` с) начинаются только
   после этого — уже за пределами бюджета edge.
2. **`uk_management_bot/api/routes/media_proxy.py:243`** —
   `httpx.AsyncClient(timeout=60)` для стрима из media-service: API-ретрай
   (`stream_with_retries`) тоже стартует через 60 с. `MEDIA_SERVICE_TIMEOUT`
   на profk не задан (дефолт 30 в settings, но этот маршрут его не читает).
3. Нет кэша оригиналов: `GET /{media_id}/file` каждый раз качает файл с
   Telegram заново (`media.py:619-643`); `preview_cache` обслуживает только
   `/preview`, а дашборд (`RequestDetailModal.tsx:881`) ходит за оригиналом.
4. Фронт при ошибке не повторяет запрос: в access-логе edge один 504 и ни
   одного повтора.

Сопутствующее (не причина, но из тех же логов): `asyncio - ERROR - Unclosed
client session` — **44 раза за 14 дней**. `get_storage_service()`
(`media.py:101`) создаёт `MediaStorageService()` → новый
`TelegramClientService` → новый aiogram `Bot` на каждый запрос; `close()`
(`telegram_client.py:239`) на этом пути не вызывается.

## Предлагаемое исправление (не применялось)

Минимальный фикс в корне, укладывающий худший случай в бюджет edge:

- `telegram_client.py:172` → `httpx.Timeout(connect=5.0, read=20.0, write=5.0, pool=5.0)`;
  с текущими ретраями худший случай connect-stall ≈ 5 + 0.5 + 5 + 1.5 + 5 = 17 с < 30 с.
  Для `self.bot.get_file` (aiogram, `AiohttpSession` дефолт 60 с) задать
  сессию с таймаутом того же порядка.
- `media_proxy.py:243` → `httpx.Timeout(connect=5.0, read=25.0, …)`, чтобы
  API не держал воркер дольше, чем живёт клиент.
- Тест: фейковый транспорт, который виснет на connect, — `download_file`
  обязан отдать ретраю управление за ≤ 6 с, а не за 60.

Отдельными пунктами (не блокеры этого бага): singleton/закрытие aiogram-сессии
в media-service; кэш оригиналов или перевод миниатюр дашборда на `/preview`;
один повтор на фронте при 5xx.

## Исправление (2026-09-09, worktree `feat+elevators`, не раскатано)

Таймауты по всей цепочке уложены в бюджет edge (30 с), TDD: три теста были
красными до правки.

| Где | Было | Стало |
|---|---|---|
| `media_service/app/services/telegram_client.py` `download_file` | `httpx.AsyncClient(timeout=60)` | `httpx.Timeout(connect=5, read=20, write=5, pool=5)` из настроек; худший случай трёх попыток 3×5 + 0.5 + 1.5 = 17 с |
| там же, `TelegramClientService.__init__` | aiogram-сессия с дефолтом 60 с (`get_file`) | `AiohttpSession(timeout=15)` |
| `media_service/app/core/config.py` | — | `telegram_api_timeout_seconds=15`, `telegram_download_connect_timeout_seconds=5`, `telegram_download_read_timeout_seconds=20` (env-переопределяемые, дефолты не требуют правок на проде) |
| `uk_management_bot/api/routes/media_proxy.py` | два клиента `timeout=60` (мета + стрим) | `_MEDIA_META_TIMEOUT` (connect 5 / read 10), `_MEDIA_STREAM_TIMEOUT` (connect 5 / read 25) |
| `uk_management_bot/api/work_reports/public_router.py` | стрим витрины `timeout=60` | тот же `_MEDIA_STREAM_TIMEOUT` (тот же дефект на публичных фото работ) |

Тесты: `media_service/test_download_retry.py::test_download_timeouts_fit_edge_budget`,
`::test_bot_api_timeout_is_bounded`;
`tests/api/test_media_proxy_streaming.py::TestTimeoutsFitEdgeBudget`;
`tests/api/test_work_reports_public.py::test_media_client_timeout_fits_edge_budget`.
Прогоны: media_service 94 passed; `tests/api tests/services` 2294 passed,
3 failed — те же три известных локальных красных, что и на main (prometheus_client,
JWT-тест); ruff чистый.

Раскатка: пересборка образов `media-service` и `api` на обоих продах
(`uk-deploy`, миграций нет). После раскатки контрольная точка — в логах
media-service новых `Response: 200 - 6x.xxx s` быть не должно.

Не вошло (отдельными пунктами): singleton/закрытие aiogram-сессии в
media-service (44 «Unclosed client session» за 14 дней); кэш оригиналов либо
перевод миниатюр дашборда на `/preview`; один повтор на фронте при 5xx.
