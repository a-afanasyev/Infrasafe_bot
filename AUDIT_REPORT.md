Полный read-only аудит монорепо на `main` `e1221993` (после PR #594, BUG-192). Стек: aiogram 3 бот + group-intake-бот, FastAPI API (REST + WS), React/Vite/TS дашборд + TWA, сателлиты `media_service`, `access_control`, `resource-accounting`, `payment_control`; PostgreSQL + Alembic (`0001…0019`), Redis, Docker Compose, Doppler. Фазы 1–5 распараллелены по 8 субагентам (архитектура / бот / API+БД / фронт / сателлиты / мёртвый код / безопасность / практики) и сведены автором. Пункты с пометкой «требует подтверждения» не проверены на проде или зависят от намерения владельца.

Предыдущие аудиты: #6 лежит в истории git этого файла, #7 — в `AUDIT_REPORT+2026-09-08+codex.md` (не отслеживается), #8 — в `docs/audit/2026-09-19-full-review.md`. ## 1. Executive summary

**P0 нет. P1 — три, и все про надёжность и эксплуатацию, а не про уязвимости.** Безопасность остаётся самой сильной фазой. Все 268 маршрутов перебраны скриптом, и каждый маршрут без auth-зависимости имеет обоснование. Межсервисные токены везде сравниваются через `compare_digest`, SQL собирается только из allowlist + bind. `npm audit --omit=dev` — 0; `pip-audit` находит одну транзитивную `ecdsa`, неэксплуатируемую (только HS256).

Главный пользовательский дефект — **альбомы фото молча теряются во всех FSM-сборщиках медиа** (A9-P1-1). `ThrottlingMiddleware` отбрасывает любое сообщение, пришедшее от пользователя меньше чем через 0,5 с после предыдущего, а альбом из N фото приходит N апдейтами за миллисекунды. Поэтому до сборщика доходит только первое фото, и ни житель, ни исполнитель об этом не узнают. Даже без троттлинга сборщики дописывают список через `get_data → append → update_data`, а это lost update при конкурентной обработке. Теста на альбом нет.

Второй сквозной мотив — **правила, которые обходит второй канал**:
- Старт смены из TWA всегда создаёт ad-hoc-смену, хотя бот по решению владельца 2026-08-24 сначала активирует идущую `planned` (A9-P1-2). В API-пути вдобавок нет аудита и уведомлений.
- В API шесть самописных Telegram-клиентов на сыром httpx мимо общего `api_bot`, без классификации 403 и в одном месте без проверки статуса (A9-P2-9).
- Житель может залить через дашборд фото с категорией `completion_*`, и бот при приёмке покажет его как фотоотчёт исполнителя (A9-P2-3).
- `file_id` из group intake принадлежит другому боту, поэтому фото таких заявок в основном боте не открываются (A9-P2-5).

Третий — **класс HTML-инъекций в Telegram до конца не зачищен**. BUG-174/178 и свип аудита #8 не дошли до карточек заявки у менеджера, модерации квартир и планирования смен (A9-P2-2). Одиночный `<` в описании, ответе на уточнение или имени в Telegram даёт 400 от Telegram, и менеджер не может открыть заявку в боте. `<a href>` превращается в живую фишинговую ссылку.

Четвёртый — **свежий код PR #559 и BUG-192 закрыт не полностью**:
- Маркер фото пишется под `FOR UPDATE`, но без `populate_existing`, поэтому лок не защищает от lost update (A9-P2-1). Мок `check_request_access` в тесте делает эту ошибку неуловимой.
- В тег-режиме group intake сообщение с `#заявка` при отказе лимитера пропадает молча, то есть ровно тот сценарий, который BUG-192 устранял (A9-P2-6).

Эксплуатационный риск: **деплой-ранбуки расходятся в наборе compose-файлов** (A9-P1-3). Канонический SKILL для profk не содержит `docker-compose.payments.yml`, поэтому рутинное пересоздание `api` по канону молча снимает `PAYMENT_SERVICE_URL/TOKEN`, и «Контроль платежей» отвечает 404/503. `Makefile prod-up` после ARCH-106 гарантированно падает.

Простота — 6/10. В боте ~2,5 тыс. строк символов, живых только в тестах, но не входящих в перечень решения владельца «оставить задел» — нужно решение. Бесспорно удаляемы ~4 тыс. строк: backfill-модули после squash-baseline, исторические скрипты (один падает на импорте, другой делает `create_all` в обход alembic), неиспользуемый SDK и ~10 мёртвых эндпоинтов media, `frontend/preview/`. pytest объявлен дважды с конфликтующими версиями: pip-audit сканирует не те версии, которые гоняют тесты, и pytest уезжает в прод-образы.

Что сделано хорошо: CI с хэш-локами, SHA-пинами, дрейф-гейтом миграций в четырёх джобах, ratchet'ами, работающими только вверх, и паритет-гейтом «compose → CI»; фоновые циклы API безопасны при нескольких воркерах (`SKIP LOCKED`, advisory-lock); fail-fast конфиг; фронт с tsc 0 ошибок, 0 `any`/`@ts-ignore` и полным паритетом i18n-ключей; payment_control — образцово маленький и корректный сервис.
