### Q1.1 Матрица прав доступа при множественных ролях

**Критичность**: 🔴 P0 - Блокирует Core Service
**Влияние**: Архитектура системы авторизации

**Контекст**:
Неясно поведение при наличии у пользователя нескольких ролей одновременно (например, житель + сотрудник).

**Варианты решения**:
1. **Максимальные привилегии** - берется роль с наибольшими правами
2. **Переключение контекста** - пользователь выбирает активную роль
3. **Композитная роль** - права объединяются с учетом ограничений

**Рекомендация**: Вариант 1 (проще в реализации)

**Ответ**: Вариант 1, заявки могут размещать все роли. Приоритет ролей админ-менеджер-сотрудник-житель/заявитель

**Требуется от бизнеса**:
- Утвердить стратегию работы с множественными ролями
- Определить приоритет ролей (admin > manager > executor > applicant)
- Решить про территориальные ограничения

### Q2.1 Условия переходов статусов заявок

**Критичность**: 🔴 P0 - Блокирует Core Service и Operations Service
**Влияние**: Бизнес-логика обработки заявок

**Контекст**:
Нужно финализировать правила автоматических переходов статусов.

**Открытые вопросы**:
1. Автоматический возврат из "Уточнение" → "В работе" через какое время? 
**ответ**: нет автовозврата при задаче вопроса заявителю, исполнитель/менеджер модет уточнить у заявителю дополнительными средствами связи (лично или по телефону) и внести уточнения от своего имени, но с указанием что было уточнения у заявителя
2. Автоматическая отмена неактивных заявок через сколько дней?
**ответ**: не активные заявки требуют актуализации раз в неделю, автозакрытие или отмена не производится
3. Можно ли вернуть заявку из "Выполнена" в "В работе"?
**ответ**: да, заявку можно вернуть если заявитель не доволен и не "принял" ее

**Текущая матрица переходов**:
```
Новая → В работе / Уточнение / Отменена
В работе → Закуп / Выполнена / Отменена
Закуп → В работе
Уточнение → В работе / Отменена
Выполнена → В работе / Подтверждена
```

**Требуется от бизнеса**:
- Утвердить финальную матрицу переходов
- Определить таймауты для автопереходов
- Решить про откат статусов

### Q6.2 Поведение при деградации сервисов

**Критичность**: 🔴 P0 - Блокирует все сервисы
**Влияние**: Архитектура отказоустойчивости

**Контекст**:
Нужно определить fallback-сценарии для каждого сервиса.

**Критические сценарии**:
1. Core Service недоступен → что делают остальные?
2. Communication Hub недоступен → как уведомлять пользователей?
3. Operations Service недоступен → можно ли создавать заявки?

**Рекомендуемая стратегия**:
| Сервис недоступен | Влияние | Fallback |
|-------------------|---------|----------|
| Core Service | Критично | Readonly режим из кеша |
| Operations | Частично | Заявки в очередь |
| Communication | Некритично | Логирование уведомлений |
| Media Storage | Некритично | Временное хранилище |
| Analytics | Некритично | Пропуск метрик |
| Integration | Частично | Работа из кеша |

**Ответ**: стратегия принята, рекомендуется при отказе Core сервиса - сообщать о недоступностии не давать информацию. 


**Требуется от бизнеса**:
- Утвердить fallback стратегию
- Определить SLA для восстановления
- Решить про уведомление пользователей о деградации
**ответ**: SLA для сервисов блокирующих работу - не более суток, для остальных - не более трех, пользователей уведомляем при действиях в боте, массовой рассылки не делавем

### Q2.3 Правила управления сменами

**Критичность**: 🟡 P1 - Влияет на Operations Service
**Влияние**: Логика планирования и учета

**Открытые вопросы**:
1. Автозавершение смен через 24 часа?
2. Минимальный отдых между сменами (8/12 часов)?
3. Максимум смен подряд (6 дней)?
4. Различия дежурных/недежурных смен?

**Рекомендации**:
- Автозавершение через 24 часа с уведомлением
- Минимальный отдых 8 часов
- Максимум 6 дней подряд
- Дежурные смены = фиксированное время

**ответ**: смены могут быть разные, деружная смена 24 часа, но пересменка может разниться, поэтому эти параметры настраиваются админом при создании шаблонов смен. смены могут быть 8*5, 8*6, 12 часов, 24 часа и так далее, мы не учитываем требования ТК и не считаем сверхурочные. нужно сделать чтобы все эти параметры настраивались через админку, так как в разных странах и разных компаниях разные требования

**Требуется от бизнеса**:
- Утвердить правила смен
- Определить типы смен
- Решить про сверхурочные
