# Техническое задание: Shared Library

## 1. Общее описание

### 1.1 Назначение
Shared Library — базовый компонент архитектуры, предоставляющий единый набор инфраструктурных и доменных решений для всех сервисов UK Management. Библиотека устраняет дублирование, обеспечивает согласованность конфигурации, безопасности, взаимодействия и наблюдаемости, а также задаёт стандарты интеграции и тестирования.

### 1.2 Цели
- Снизить операционные риски за счёт унифицированных практик.
- Ускорить разработку новых сервисов и функций.
- Обеспечить единые контракты и схемы для межсервисного взаимодействия.
- Гарантировать соблюдение требований безопасности и наблюдаемости.

### 1.3 Область применения
- Backend‑сервисы: Core, Operations, Communication Hub, Media Storage, Analytics, Integration Hub, AI/ML.
- Инструменты администрирования и DevOps‑решения.
- Тестовые и вспомогательные утилиты, использующие общие контракты.

### 1.4 Ограничения
- Библиотека не управляет хранением секретов, а определяет интерфейсы работы с ними.
- Конкретные реализации (язык, фреймворк) выбираются командами сервисов, соблюдающими описанные контракты.
- Бизнес‑правила, не утверждённые (например, матрица прав доступа), должны переопределяться на уровне сервисов.

## 2. Архитектура библиотеки

### 2.1 Структурные области
- **Foundation**: настройки, исключения, перечисления, типы идентификаторов.
- **Domain Schemas**: модели пользователей, заявок, смен, событий, справочников, с валидацией и расширяемыми полями.
- **Data Access**: менеджеры подключений к хранилищам, фабрики сессий, шаблоны репозиториев, пагинация, аудит.
- **API Toolkit**: унифицированные структуры ответов, обработка ошибок, фильтры, CRUD‑шаблоны.
- **Messaging**: публикация/подписка событий, формат сообщений, политика маршрутизации, работа с очередями и DLQ.
- **Security**: управление токенами, авторизация, rate limiting, защита входного/выходного трафика.
- **Clients**: стандартизированные межсервисные вызовы, политики ретраев, circuit breaker, fallback.
- **Observability**: логирование, метрики, трассировка, корреляция запросов.
- **Testing & Tooling**: шаблоны контрактных тестов, фикстуры, средства симуляции очередей и хранилищ.
- **Utilities**: генерация идентификаторов, нормализация данных, вспомогательные операции.

### 2.2 Интеграционные принципы
- Контракты и схемы публикуются как часть документации библиотеки и версионируются.
- Любая реализация должна поддерживать асинхронную и синхронную работу.
- Все расширения оформляются через публичные интерфейсы; прямое изменение внутренних модулей запрещено.

## 3. Конфигурация и управление жизненным циклом

### 3.1 Модель настроек
- Идентификатор сервиса, версия, окружение, режим выполнения.
- Подключения к БД, кешам, очередям, внешним API (URL, параметры пулов, таймауты).
- Параметры безопасности: выбранный алгоритм подписи, пути к ключам/секретам, сроки действия токенов, политика ротации.
- Политики rate limiting (лимит, окно, ответ при превышении), настройка CORS, ограничения размеров запросов.
- Настройки наблюдаемости: уровень логов, включение метрик, параметры трассировки.

### 3.2 Управление ресурсами
- Менеджер подключений обеспечивает ленивую инициализацию и повторное использование ресурсов.
- Фабрика сессий обрабатывает транзакции, фиксирует или откатывает изменения, закрывает соединения.
- Предусмотрен режим тестирования без пула соединений и с фиктивными ресурсами.
- Определены интерфейсы для инициализации и завершения (lifespan hooks), включая обработку ошибок при остановке.

### 3.3 Работа с секретами
- Библиотека предоставляет контракты для получения ключей/паролей из внешних хранилищ.
- Поддерживается как симметричная, так и асимметричная криптография; приватные ключи не распространяются между сервисами.
- Обязательная документированная процедура ротации ключей и уведомления зависимых сервисов.

## 4. Модели и данные

### 4.1 Базовые сущности
- Пользователь: идентификаторы, контактные данные, роли, статусы верификации, метаданные.
- Заявка: атрибуты, местоположение, приоритет, статусы, таймлайны, связи с медиаданными.
- Смена и назначение: планирование, исполнители, параметры расписаний, статистика загрузки.
- События: структура сообщений, метаданные источника, версия, полезная нагрузка.
- Справочники (здания, адреса, интеграции): идентификаторы, состояния, ссылки на внешние системы.

### 4.2 Правила валидации
- Ограничения длины, форматы (номер телефона, идентификаторы, временные диапазоны), обязательность полей.
- Возможность переопределения правил (например, матрицы переходов статусов) через конфигурацию сервиса.
- Поддержка локализации и мультиязычности (языковые коды, форматированная выдача).

#### Стандартизированные лимиты текстовых полей (Q4.2)

**Лимиты полей**:
- Описание заявки: 10-2000 символов
- Комментарий: 5-1000 символов
- Причина отмены: 10-500 символов
- ФИО пользователя: 5-100 символов
- Адрес здания: 10-500 символов
- Примечания к смене: 0-500 символов

**Правила форматирования**:
- ✅ Emoji разрешены (Unicode support)
- ❌ Markdown не поддерживается
- ❌ HTML экранируется
- ✅ Переносы строк разрешены (до 20 строк)
- ✅ Спецсимволы экранируются

**Валидация**:
Библиотека предоставляет функции валидации для всех типов текстовых полей с:
- Проверкой длины (min/max)
- Экранированием HTML тегов
- Удалением Markdown форматирования
- Поддержкой Unicode emoji
- Обработкой спецсимволов
- Нормализацией пробелов и переносов строк

### 4.3 Работа с данными
- Репозитории реализуют контракты чтения/записи, фильтрации, пагинации, сортировки.
- Поддержка мягкого удаления, аудита действий, журналирования изменений.
- Рекомендации по индексированию и лимитам выборки для предотвращения деградации производительности.

## 5. Взаимодействие и интеграции

### 5.1 Контракты событий
- Формат: идентификатор события, тип, версия, временная метка, источник (сервис, инстанс, версия), correlation и causation id, метаданные, полезная нагрузка.
- Маршрутизация: сохранение исходных routing key (например, `request.created`) для совместимости с pattern‑matching (`request.*`, `request.#`).
- Гарантии доставки: подтверждение, повторная отправка с экспоненциальной задержкой, сохранение в DLQ, идемпотентность обработчиков.
- Версионирование: правила добавления/удаления полей, документирование breaking changes.

### 5.2 Межсервисные клиенты
- Единые заголовки (корреляционные идентификаторы, версия клиента, информация о вызывающем сервисе).
- Политика таймаутов, ретраев, circuit breaker (порог ошибок, окно наблюдения, fallback).
- Логирование запросов и ответов с маскированием конфиденциальных данных.
- Управление зависимостями: контракты для HTTP, gRPC, message‑based взаимодействия.

### 5.3 Событийно‑управляемые процессы
- Поддержка саг, компенсационных действий, согласованных транзакций.
- Конфигурация приоритетов очередей, обработка фоновыми исполнителями, мониторинг задержек.

## 6. Безопасность

### 6.1 Аутентификация
- Поддержка симметричных и асимметричных алгоритмов подписи токенов.
- Проверка сроков действия, типа токена, схемы выдачи.
- Политика хранения и ротации секретов, механизм уведомления зависимых сервисов.
- Возможность включения дополнительных утверждений (claims) и проверки прав доступа.

### 6.2 Авторизация
- Базовый набор ролей (applicant, executor, manager, admin, системные роли).
- Возможность переопределения матриц полномочий и правил перехода статусов на уровне сервисов.
- Механизмы проверки прав (access guards, middleware) и шаблоны для ограничений (территориальные, временные, контекстные).

### 6.3 Защита периметра
- Rate limiting по идентификатору пользователя, API‑ключу, IP‑адресу.
- Обработка подозрительных действий, блокировка по спискам (blacklist/whitelist), уведомления об аномалиях.
- Контроль форматов ввода, защита от XSS/CSRF/SQL‑инъекций, ограничение размеров полезных нагрузок.

## 7. Наблюдаемость и эксплуатация

### 7.1 Логирование
- Структурированный формат с обязательными полями (время, уровень, сервис, сообщение, trace id, span id).
- Требования к маскированию PII и секретов.
- Поддержка разных профилей вывода (production — JSON, development — человекочитаемый).

### 7.2 Метрики
- Набор стандартных метрик: HTTP‑запросы (счётчики, гистограммы), операции БД, события, кеш, фоновые задачи.
- Метрики сервиса (версия, окружение) для дашбордов.
- Встроенные декораторы/обёртки для измерения длительности и статусов выполнения.

### 7.3 Трассировка
- Генерация и распространение correlation id/spans.
- Интеграция с внешними системами распределённого трейсинга.
- Регламент минимального набора атрибутов для видимости бизнес‑операций.

## 9. Управление версиями и процесс

### 9.1 Версионирование
- Семантическое (MAJOR.MINOR.PATCH). Минорные релизы — обратная совместимость; мажорные — обязательный migration guide.
- Документация изменений: changelog, список breaking changes, инструкции по обновлению.
- Поддержка канала «next» для предварительных версий, оговорки о сроках поддержки.

### 9.2 CI/CD и публикация
- Обязательные проверки: статический анализ, тесты, проверка контрактов, генерация документации.
- Публикация в приватный реестр, хранение артефактов с цифровой подписью.
- Процесс отката: возможность вернуться на предыдущую стабильную версию без изменения сервисов.

### 9.3 Процесс изменения
- RFC/issue процесс для добавления новых модулей или изменения контрактов.
- Ревью архитектора и представителей команд‑потребителей.
- Критерий приема изменений: доказанное повторное использование, тесты, обновлённая документация.
